Главный вывод: критическая просрочка при хорошем техническом фундаменте
По ТЗ (октябрь 2025 → финальный релиз 25.03.2025) портал просрочен на 17+ месяцев. При этом анализ исходного кода живого приложения на b2b.laparet.ru показывает, что ядро системы реализовано: авторизация, заказы, каталог, аналитика, ценообразование, возвраты, претензии, счета, файлообменник, программа лояльности — все есть в бандле. Критически недоделаны: Академия (обучение), полноценный модуль доставки, управление пользователями, API тонко заполнен. ViHome 2.0 содержит ряд очень сильных идей, но большинство из них — пожелания без приоритизации.

Оценка идей ViHome 2.0
Критический разбор 24 предложенных фич — что имеет ценность, а что — перегруз

Документ ViHome 2.0 содержит 24 направления развития. Многие из них инновационны и реализуемы. Ниже — честная приоритизация по критериям: влияние на продажи, реализуемость за разумный срок, уникальность на рынке B2B плитки.

🔥 ВЫСОКАЯ ЦЕННОСТЬ — реализовывать в первую очередь
Приоритет 1
AI-ассистент продавца
(поиск аналогов, upsell)
Продавец описывает запрос клиента — AI за секунды находит 3 подходящих позиции + аналоги + сопутствующие товары. Прямое влияние на конверсию и средний чек. Реализуется через LLM + векторный поиск по каталогу. Аналогов у конкурентов-дистрибьюторов плитки пока нет.
AI +Revenue 3-4 мес
Приоритет 2
AI поиск аналога
по фото конкурента
Продавец фотографирует образец у конкурента — AI ищет аналог в ассортименте Laparet. Killer feature для торгового зала. Технически: мультимодальная модель (CLIP или GPT-4V) + каталог с изображениями. Даёт конкретное конкурентное преимущество на точке продаж.
AI + Vision Конкурентное преимущество 4-6 мес
Приоритет 3
AI-прогнозирование спроса
для автозаказа
На основе истории ТТ, сезонности и региональных трендов — AI формирует готовый черновик заказа для закупщика. Снижает неликвид и дефициты. Реализуется на ML-модели временных рядов. Прямая экономия денег клиента = лояльность.
AI/ML Снижение неликвида 5-7 мес
Приоритет 4
AI-сбор отзывов из
2ГИС и Яндекс.Карт

AI + NLP Управление качеством 2-3 мес

Фичи, которые стоит отложить или переосмыслить
«AI Болмат-эксперт» (видеоаватар) — синтезированный видеоаватар конкретного человека создаёт юридические и репутационные риски. Вместо него достаточно текстового/голосового AI-ассистента без привязки к личности.

Хит-парад конкурентов — хорошая идея для сбора рыночной разведки, но продавцы не будут это делать добровольно. Нужно встроить в более естественный процесс.

Электронные чеки — регуляторный вопрос в России, требует отдельной проработки с юристами.

ViHome3D/VR-интеграция как основной фокус — мощный инструмент, но сначала нужно закрыть базовый функционал портала. ViHome3D — это на следующий этап.

MCP-интеграция: потенциал обмена данными
Model Context Protocol — следующий рубеж B2B-автоматизации
🔌 Что такое MCP применительно к LAPARET B2B
MCP (Model Context Protocol, стандарт Anthropic 2024) — открытый протокол для подключения AI-агентов к внешним системам. Проще говоря: любой AI-агент — у партнёра, у Баусервиса или у внешнего разработчика — может подключиться к порталу через стандартизированный интерфейс и автономно выполнять действия: запрашивать остатки, цены, создавать заказы, получать аналитику.
Это не просто API — это AI-native интеграция. Разница: обычный API требует разработки коннектора под каждую систему. MCP — это стандарт, как HTTP: один раз реализовал сервер, и любой AI-клиент подключается по протоколу.
🏪
MCP-сервер для партнёров
Крупные ТТ с IT-командами или AI-агентами получают MCP-доступ к порталу. Агент закупщика автономно: мониторит остатки, создаёт черновики заказов при снижении запасов ниже порога, запрашивает прайс с учётом персональных условий. Без UI, без ручного труда.
🤝
MCP-клиент внутри Баусервис
Внутренний AI-агент Баусервиса подключается через MCP к 1С, CRM и порталу. Автоматически: отслеживает просроченную дебиторку, формирует коллекционные предложения, уведомляет менеджеров о рисках — без ручного сбора данных из разных систем.
📦
MCP-хаб для поставщиков
Поставщики (бренды плитки) подключаются через MCP и видят агрегированные данные о продажах их SKU в сети, дефицитах, прогнозах. Это принципиально меняет партнёрские отношения — данные о спросе в реальном времени вместо ежемесячных отчётов.
💡
Реализация MCP: что нужно
1. MCP-сервер поверх существующего REST API — это тонкий адаптерный слой, не переписывание. 2-3 недели разработки при наличии документированного API.

2. OAuth 2.0 + scope-based permissions — партнёр авторизует своего AI-агента как отдельную сущность с ограниченными правами (только заказы, только чтение и т.д.).

3. Tool-манифест — описание доступных инструментов: get_stock, create_order, get_prices, get_analytics. Любой LLM-агент с поддержкой MCP подключается автоматически.

Важно: первыми в российском рынке B2B стройматериалов, внедрившими MCP, получат огромное конкурентное преимущество в привлечении технологически продвинутых партнёров.

Рекомендации и план действий
Что делать прямо сейчас, чтобы закрыть долг и выйти вперёд рынка
  • 1
    Немедленно: актуализировать тестовые данные и провести полный аудит с доступом
    Тестовые учётные данные (Anton/Anton1 и др.) не работают. Необходимо: получить рабочие credentials от подрядчика → пройти портал под каждой из 3 ролей → составить полный список работающих и сломанных функций. Без этого любая приёмка — вслепую.
    → Горизонт: 1–2 дня
  • 2
    Критически: провести приёмочное тестирование по чек-листу ТЗ
    По каждому пункту раздела 5 ТЗ («В рамках первого релиза реализуются») — формальная проверка с фиксацией: работает / не работает / частично. Особое внимание: синхронность данных заказов с 1С через Kafka, корректность расчёта бонусов, разграничение прав по ролям (RBAC). Результат — акт приёмки с перечнем дефектов.
    → Горизонт: 1 неделя
  • 3
    Срочно: закрыть критические gap'ы перед боевым запуском
    Три обязательных блока к боевому запуску: (а) Управление пользователями — без этого Руководитель не может создавать/удалять сотрудников самостоятельно; (б) Безопасность — хотя бы двухфакторная аутентификация для роли Руководитель; (в) Академия — минимальная версия (5–10 курсов, тест, баусы за прохождение). Без Академии программа лояльности работает вполсилы.
    → Горизонт: 4–6 недель
  • 4
    Среднесрочно: запустить AI-ассистента продавца как первую AI-фичу
    Это наиболее реализуемая и наиболее ценная AI-инновация из ViHome 2.0. Архитектура: векторная база данных каталога + LLM с system prompt о продуктах Laparet + интерфейс в мобильном приложении. Срок разработки: 3–4 месяца при наличии хорошего подрядчика. Метрики успеха: увеличение среднего чека в ТТ, сокращение времени подбора товара.
    → Горизонт: 3–4 месяца
  • 5
    Среднесрочно: AI-мониторинг отзывов из геосервисов
    Быстрая победа с высокой ценностью для руководителей сети ТТ. Техническая реализация простая: парсинг 2ГИС/Яндекс.Карт + LLM-анализ тональности → дашборд в существующем разделе аналитики. Примерный срок: 2–3 месяца. Немедленно даёт ценность для управления качеством сети.
    → Горизонт: 2–3 месяца
  • 6
    Стратегически: спроектировать MCP-сервер поверх B2B API
    Начать с прototипа: подключить внутреннего AI-агента Баусервиса к порталу через MCP. Показать руководству, как агент автономно создаёт черновик заказа по данным из 1С. Это демо станет сильнейшим аргументом для крупных партнёров и позиционирует Баусервис как технологического лидера рынка. Затем — открытый MCP-доступ для партнёров.
    → Горизонт: 6–9 месяцев
8
Контрольные вопросы подрядчику
Список вопросов для встречи по статусу проекта
  • Kafka + 1С: покажите в живом режиме создание заказа на портале и отображение его в 1С в течение 30 секунд. Это приёмочный критерий №2 из ТЗ.
  • RBAC: создайте нового пользователя роли «Продавец» под логином Руководителя и убедитесь, что он не видит финансовые данные Руководителя.
  • Данные: проверьте совпадение суммы трёх последних заказов в 1С и в портале — есть ли расхождение?
  • Академия: есть ли хоть один завершённый курс с тестом и начислением баусов?
  • Производительность: ТЗ требует отклик ≤2 сек. Есть ли результаты нагрузочного тестирования? При какой нагрузке (кол-ве одновременных пользователей)?
  • Безопасность: есть ли лог пользовательских действий (кто, когда, что изменил)? Это требование ТЗ п.7.
  • Доставка: реализован ли полный модуль доставки с маршрутами льготных доставок и предварительным набором?
  • Управление пользователями: может ли Руководитель самостоятельно создать нового Продавца прямо в портале, без обращения к администратору?
